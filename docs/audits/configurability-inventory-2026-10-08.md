## 一句话结论

**现在写死、但明显应该可调的值至少 20 处；而这 20 处里没有一处能改在面板上。**

原因是两条结构性事实（都是实测）：

1. **面板白名单没有数值类键。** `operator_config.SETTINGS` 一共 32 个键（`bool` 10 / `str` 13 /
   `secret` 7 / `csv` 2，实测枚举），`kind` 只有 `bool` / `str` / `csv` / `secret` 四种，
   **没有 number**。也就是说面板能开能关、能填地址与 key，但**任何一个数字都改不了**。
   （键数会随版本漂，**"零数值键"这个结构性结论才是不变的那个**。）
2. **`dev_config` 是 import 期求值。** 它的常量在模块导入时算一次，所以"改环境变量"
   只在下次启动生效——这是"需重启"的默认形态。而这个仓库里**唯一能热更数值的机制**
   是少数几个函数式读法（`persona_offset_hours()`、`reply_api_base_url()` 等，见
   `dev_config.py:294-297`）与 `runtime_flags` / `operator_config` 这十个布尔开关；
   数值没有这待遇。

   **这一条是"纪律已写、照抄会踩"，不是"今天已经有一个键在骗人"。** 实测核查：
   白名单里标 `live` 的值确实都走**调用时现读**（`runtime_flags` 对象、`model_config._read()`），
   标 `restart` 的三个审批项也是如实标注——**今天没有哪个键在骗人**。
   同类事故在本仓确实发生过一次（`runtime.py:320-333` 记录了"import 期常量 + 环境被写空"
   那次 key 变空、全 401），所以这条纪律值得写在前面。

于是现状只能落到两档：**写死 ✗** 或 **环境变量 ✓（需重启）**。
