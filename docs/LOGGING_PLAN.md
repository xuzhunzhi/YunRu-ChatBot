# 日志设计（用户 2026-10-08 夜定稿）

> 这份是**需求记录**，不是实现说明。用户的原话在每节开头引用，下面是要做成的形状。

## 一、两类日志**完全不一样**（用户原话：*"开发用的日志和日用的日志完全不一样"*）

| | 日用日志 | 开发日志 |
| --- | --- | --- |
| 回答什么 | **她做了什么** | **她为什么这么做** |
| 谁看 | 用户本人；将来面板/群管理员看**脱敏版** | 开发者（我）与用户排查时 |
| 内容 | 收发消息 · 决策与规则判定 · 发送结果 · 插件业务动作 | 完整提示词与模型原文 · 原始事件 · 验证留痕 · 探针产物 |
| 保留 | 长（可复盘的历史） | 短、滚动、**可一键关** |
| 能不能给外人看 | 脱敏后可以 | **绝不** |

**推论**：面板（现在与将来的管理员控制台）**只能读日用日志** ✗ 开发日志永远不给面板。
（用户 2026-10-08 提过"日志分成两份不就好了"—— 就是这个意思。）

## 二、Stage 3 的日用日志分三条流（用户原话：*"stage3的日志分成消息日志和模型日志还有规则日志"*）

1. **消息日志** —— 收到了什么、发出了什么（含分段、消息 id、发送结果）← 现有 `chat.jsonl` 已覆盖大部分
2. **模型日志** —— 每次模型调用的**对象、耗时、成功失败**（原文归开发日志）
3. **规则日志** —— **哪条规则在哪一步做了哪个判断** ← **现在没有，这是缺口**

**插件的日志各自单独成流** ✗（用户原话：*"插件这些单独做日志"*）：
邮件 · 识图 · 入群审批 · 群管理 · 面板 · 掉线通知 —— 各一份，不混进 Stage 3 的流。

## 三、目标：**每个动作都可还原、都可以复盘**（用户原话）

要还原一轮对话，需要两样东西：

1. **回合号（turn id）** —— 同一轮的消息、模型调用、规则判定**都带上它**，三条流靠它对得上；
2. **规则流按行记判断** —— `{回合号 · 时间 · 会话 · 哪一步 · 哪条规则 · 结论 · 依据}`，
   例如：注意力为什么被触发 · 判定说 KEEP/EXIT 及理由 · 没被叫到时因哪条规则不出声 ·
   审核打回重写（什么理由）· 数据边界记号命中后重试或丢弃 · 分段几段、发送成功还是补发。

判据：**顺着回合号，能从"谁说了什么"一路读到"她为什么说这句、中间哪一步拦了她"**，
不用像 2026-10-08 那样靠翻日志猜。

## 四、排期与前提

- 属于**核心（Stage 3）**改动：穿回合号 + 新增规则流 + 各插件日志成流；
- **等当前小队列清完**再派；插件那部分要动插件树（一次一棵树一个 agent）；
- 面板读哪一份、脱敏到什么程度，**等真有群管理员时再定**（不为没有消费者的需求预先造插座）。
